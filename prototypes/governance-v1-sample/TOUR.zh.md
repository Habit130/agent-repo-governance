# 版本 1 写进样例仓库的治理：导览

原型，用完即弃，不合并。样例仓库 tally 是虚构的：一个小型命令行计时工具，可以同步到网上的服务。它有一个 CI 检查（叫 test），有一处认证代码，还有一个发布脚本。

## 结论先说

- 版本 1 往样例仓库写 15 个文件。每个会话开工只读其中 3 到 4 个，合计约 13 到 25 KB。
- 每条规则只有一个归处。起草时发现 5 处重复，都已去掉。唯一保留的副本是给 Bugbot 的规则文件，这是之前定好的。
- 走查发现 5 个缺口，都需要 habit 拍板，见文末问题。
- habit 最能感受到的一个代价：仓库自有的治理内容也算敏感路径，包括 AGENTS.md 的“本仓库”一节和构建命令。所以哪怕只改一条测试命令，也是中等风险 PR，要 habit 开评审者。这是已定敏感路径清单的直接后果，见问题 1。

## 文件导览

类别说明：

- **固定**：每个仓库都一样，文件开头有一行“由治理模型版本 1 生成，只有生成器能改”。升级时整份替换，用逐字比对来核查。
- **确认值**：生成器提出，habit 在初始化时确认，存在治理记录里。
- **仓库自有**：初始化时写一次，之后由本仓库的普通 PR 维护，升级不碰。

## 样例仓库里 habit 确认的值

- 认证代码是敏感路径，改它至少中等风险。
- 发布脚本是敏感路径，底线定为高风险。
- 必需检查：本仓库的 test 和门禁。
- 原有贡献指南里的四条规则：
  - 两条兼容，搬进 AGENTS.md 的“本仓库”一节：测试不连真实服务；用户能看到的改动要写更新日志。
  - 一条已被模型覆盖，删掉并列出：只用压缩合并。
  - 一条与模型冲突，删掉并单独列给 habit：维护者可以直接推到主分支。

## 走一遍中等风险交付

例子：给 tally 加一个命令，把计时记录导出成表格文件。用户能看到这个变化，所以是中等风险；它不碰敏感路径。

1. habit 把想法告诉规划者。规划者先读总规则和规划者手册，跟 habit 把需求问清楚，再写一张工单，内容是做什么、验收标准、用哪些技能、验证命令，不写风险等级。habit 批准后，规划者在终端给出两段式开工指令。**habit 出场：提想法、批准工单。**
2. habit 开一个构建者会话，粘贴开工指令。**habit 出场：派发。**
3. 构建者先读总规则、构建者手册、共用评审规则、工单和构建命令。然后认领工单，建自己的独立工作区和分支，先写测试再实现，跑工单里的验证命令，提交。
4. 自查：构建者开一个不带任何对话记忆的子代理，按评审规则审这次改动，并独立判断风险等级。它判为中等。
5. 构建者推送，按 PR 模板开 PR，写上“风险：中等，新增一个用户能看到的命令”，再贴一条证据评论：跑了什么、结果如何、改动前后的对比。
6. GitHub 自动跑两项必需检查。门禁读主分支上的治理记录：作者可信，写了风险等级，没碰敏感路径，于是通过。另一项是本仓库的测试。
7. 构建者请 Bugbot 评审。Bugbot 按自己的规则文件审。构建者逐条处理，“必须处理”的问题要么修好，要么拿证据驳回。
8. 构建者在终端给 habit 一份两段式交接。“给 habit”一段说开哪个工具、用哪个模型；中等风险不要求换厂商。“粘贴给 agent”一段是评审者的开工指令。然后构建者在 PR 上等。
9. habit 开评审者会话。**habit 出场：开评审者，属于派发。**
10. 评审者读总规则、评审者手册、共用评审规则、工单和 PR，看不到构建者的对话。它在自己的检出里重跑验证命令，自己判断风险等级（只能调高），全面审查，并判断构建者对 Bugbot 问题的处理。最后在 PR 上发一条评审，再给出一个“通过”或“不通过”的状态。
11. 如果有“必须处理”的问题，构建者修好后推送。新提交会重新跑门禁、测试和 Bugbot，评审者只复审改动的部分，最多三轮。双方在 PR 上互相等待。如果某个工具不能等，它会停下来说明在等什么，这时 habit 去那个终端说一声“继续”。**habit 可能出场：说“继续”。**
12. 审查通过后，评审者先确认两件事：每项必需评审都在当前这个提交上通过了；规则集仍然生效。然后它在 PR 上发英文合并摘要，再在终端给 habit 中文摘要，内容是：
    - 等级、结论、各类问题数；
    - 改了什么；
    - 验收标准逐条是否达到；
    - 证据；
    - 每个评审者发现了什么、怎么处理的；
    - 检查没覆盖到的地方；
    - 怎么回滚。

    摘要后面跟一条锁定到当前提交的合并命令，以及下一张工单的开工指令。
13. habit 读摘要，运行合并命令。**habit 出场：合并。** 门禁和测试必须是绿的，否则 GitHub 拒绝合并。如果期间有人又推送了新提交，这条命令会直接失败。
14. 合并后工单自动关闭。主分支上自动跑的测试就是冒烟检查。构建者删掉自己的工作区，这一步有个缺口，见问题 8。

中等风险下，habit 共出场四次：提想法并批准工单、开构建者、开评审者、合并。偶尔还要说一声“继续”。这和之前定好的四个接触点一致（计划、派发、升级、合并），开评审者算作派发。

**低风险的不同之处：** 没有评审者。Bugbot 通过后，由构建者自己完成确认、写合并摘要、给出合并命令。如果构建者想驳回 Bugbot 的“必须处理”问题，PR 升为中等，交给评审者裁决。habit 少出场一次。

**高风险的不同之处：**

- 评审者必须用另一家厂商的模型。
- 第二个评审机器人 Codex 只响应 habit 自己的账号，所以每出一个新提交，habit 都要运行一次构建者给的请求命令，最多三次。**额外出场。**
- 涉及认证、隐私或密钥时，评审者要加跑安全评审。
- 要求更严：提供改动前后的行为证据；不可逆操作先在副本上演练；每个小问题都要回复；PR 只放高风险的那一部分。
- 合并摘要升级为高风险报告，多三项：为什么是高风险、演练结果、哪些步骤等 habit 批准。
- 合并后，构建者确认测试为绿，跑冒烟命令，再逐个请 habit 批准每个不可逆步骤。**额外出场：habit 回到构建者的终端。**

**如果这次改动碰了敏感路径：** 碰认证代码，风险至少要中等；碰发布脚本，至少要高。等级写低了，门禁会拦下，habit 也合并不了。

## 给 habit 看之前做过的检查

- 每个固定文件都带那一行生成说明。混合文件写明说明只管哪一部分。
- AGENTS.md 最终约 8 到 10 KB，占 Codex 读取上限（32 KB）的三成左右。
- 每条规则只在一个文件里写，其他文件只指过去。对照表在同目录的英文说明里。
- 起草时去掉了 5 处重复：工单冻结、认领、派发、自查说明、确认值的规矩。
- 唯一保留的副本是 Bugbot 规则文件。它和 AGENTS.md 由同一个模板生成，并由逐字比对保证一致。

## 几个机械性的小选择

以下几点没有工单决定过，都是机械性的选择，habit 可以否决：

- 治理记录、所有者脚本、门禁的文件位置和名字，以及门禁检查的名字。
- AGENTS.md 里固定部分的起止标记。
- 回滚 PR 的写法：模板里不放现成的那一行，只在注释里说明怎么写；写错了，门禁会直接说明怎么改。
- Cursor 的整个配置目录都算敏感路径。
- 交给 habit 的合并命令和 Codex 请求，都写成 habit 自己账号的命令，因为这台机器上默认的身份是 agent 账号。

## 第 1 轮问题

每题都给了建议答案，回答“是”即采纳建议。

**Q1 够轻吗？**
- 15 个文件，每个会话开工只读 3 到 4 个。
- 代价：改仓库自有的治理内容，例如改一条测试命令，或者加一条像“写更新日志”这样的仓库规则，都是中等风险 PR，需要 habit 开评审者。

建议：够轻，不删文件，也接受这个代价。这些文字指挥着每一个 agent，改动时值得有一个独立的评审者看一眼。

**Q2 有缺漏或重复吗？**
- 重复已经清理完。唯一的副本是 Bugbot 规则，这是之前定好的。
- 缺漏只找到 Q7 和 Q8 两处。

建议：除 Q7、Q8 外，没有缺漏也没有重复。

**Q3 流程读起来对吗？**
- 中等风险下，habit 出场四次：批准工单、开构建者、开评审者、合并。偶尔要说一声“继续”。
- 高风险额外有两件事：每出一个新提交，habit 运行一次 Codex 请求命令，最多三次；合并后，habit 回到构建者的终端，逐个批准不可逆步骤。

建议：对。这些额外动作都在已定规则之内，不需要改。

**Q4 评审规则只放在 AGENTS.md 吗？**
- 这里说的是三样东西：风险等级的标准、问题分类及其对应关系、“风险等级写低了就算必须处理的问题”这条规则。
- 之前两张工单给了它们两个家：
  - 《How work flows from idea to merged PR》说放在共用评审规则文件；
  - 《How one canonical policy reaches every harness》说放在 AGENTS.md 的评审规则一节，因为 Codex 机器人只读那里。
- 一条规则只能有一个家。

建议：放在 AGENTS.md 的评审规则一节。共用评审规则文件只讲这些规则怎么用。记为对《How work flows from idea to merged PR》的修订。

**Q5 AGENTS.md 加两节吗？**
- 有几条规则对所有角色都适用，却不属于任何一本角色手册：
  - 怎么跟 habit 说话：用中文，不贴代码，署上自己的角色，开会话的请求分两段。
  - 治理文件的规矩：固定文件不要改；确认值只按 habit 的原话改；仓库的治理规则和技能说明冲突时以仓库为准；缺了需要的技能就停下。
- 已定的 AGENTS.md 内容清单里没有它们的位置。

建议：在 AGENTS.md 加这两节，各自保持简短。记为对《How work flows from idea to merged PR》的修订。

**Q6 门禁按每条路径自己的底线来拦吗？**
- 《Which rules are enforced deterministically》写的是：碰了敏感路径，风险至少要中等。
- 但 habit 可以给个别路径定高风险底线，比如样例里的发布脚本。
- 照现在的写法，改发布脚本时写成中等也能通过门禁，高底线只能靠评审者发现。

建议：门禁按每条匹配路径自己的底线检查，高底线也由门禁拦下。确认属实的纯回滚照旧豁免。记为对该工单的修订。

**Q7 版本 1 接受机器人看不到仓库专属的评审规则吗？**
- 两个评审机器人只读固定的文字：AGENTS.md 的评审规则一节，以及 Bugbot 规则。
- 所以样例里“用户能看到的改动要写更新日志”这样的仓库规则，构建者和评审者看得到，机器人看不到。

建议：版本 1 接受这个限制，不在机器人的规则里给仓库留加内容的口子。在《How the generator turns a repository's state into its governance》里写明这一点；以后需要时再出新版本。

**Q8 中、高风险合并后，构建者怎么知道已经合并？**
- 已定流程要求构建者在合并后删掉工作区。高风险时，它还要跑冒烟命令，再请 habit 批准。
- 但中、高风险的合并命令是评审者给 habit 的，没有人通知构建者。

建议：
- 构建者交接之后，一直在 PR 上等到合并，和其他等待一样。
- 如果它所在的工具等不了，就不等了。留下的工作区没有害处，也不打扰 habit。
- 高风险时，评审者给 habit 的消息里写明：合并后去构建者的终端说一声“已合并”。

记为对《How work flows from idea to merged PR》的修订。

**Q9 上一节的机械性小选择都接受吗？**

建议：全部接受，最终写法交给规格去定。
